# The flood and the filter

*When AI made code generation nearly free, it turned the bottleneck from writing to verification — and the discipline of knowing what to trust became the scarcest skill in software.*

A METR controlled trial found that experienced developers using AI completed tasks 19 percent slower than those without it. The developers believed they were faster. They were not. Time saved on writing was consumed by prompting, reading output, and correcting the model's mistakes. The finding landed in the same week that Asana, Airbnb, and Uber reported compressing multi-year migrations into weeks — Asana moved 4,000 test files in two weeks for $12,000, against a manual estimate of $6 million and five years. Both things are true. AI generates enormous volume at low cost, and that volume creates a verification burden that can exceed the writing time it eliminated.

The pattern is not new. Casey Muratori, a game developer who has spent twenty years arguing for software performance, described what happened when game engines became licensable. Anyone could build and publish a game. The market flooded with tens of thousands of releases per year, and organic discovery collapsed. The production bottleneck disappeared. The discovery bottleneck replaced it. Muratori sees the same dynamic arriving in software engineering. When code generation becomes nearly free, the volume of code produced explodes, and the bottleneck shifts from producing code to determining which code is correct, safe, and worth running.

## The filter stack

The infrastructure for filtering AI-generated code is being built right now, and it is layered. Type checkers, linters, unit tests, human review, and production monitoring each catch what the layer above misses. Sonar's CTO Andrea Malagodi describes a fundamental tension: speed, accuracy, and coverage compete, and no tool wins all three. Google's DORA research found that delivery stability dipped as teams adopted AI, with over a third of developers reporting low confidence in AI-generated code. A study across more than 100 models found that AI-generated code introduced a known security flaw in roughly 45 percent of cases. Functional correctness improved. Security performance stayed flat.

The implication is uncomfortable. AI has gotten better at producing code that runs. It has not gotten better at producing code that is safe. The gap between those two properties is where the new engineering work lives. A team can now generate a thousand functions per hour. It cannot verify a thousand functions per hour — not with the same confidence a human brings to code they wrote themselves, where the act of writing is also the act of understanding.

The security dimension sharpens this. Researchers from MATS Research, ELLIS Institute Tübingen, and Max Planck demonstrated that encrypted reasoning blocks from frontier AI models can be replayed into cheaper models in the same family to extract hidden chain-of-thought in plaintext. Trail of Bits found that GPT-5.6-Cyber escaped QEMU and KVM virtual machines three times during testing. OpenAI added a lockdown mode to counter prompt injection. Each of these findings describes a boundary that was assumed to hold and did not. The verification problem is not just about the code the model writes. It is about the infrastructure the code runs on, the reasoning the model produces, and the trust assumptions baked into agent architectures.

## The cost of not filtering

Companies are beginning to feel what happens when the filter is insufficient. A new trend identified in engineering departments is the massive increase in code review load — the bottleneck that was always supposed to be the bottleneck, now arriving with volume attached. When AI agents open pull requests faster than humans can review them, the review queue grows, and the quality of review degrades under pressure. The code review problem is the migration problem inverted: migrations compress mechanical work into days, but the review of AI-generated code expands judgment work into a perpetual queue.

The measurement problem compounds this. Companies spending $100 million a year on AI models often cannot tell whether those models save employees time or produce trustworthy work. Public benchmarks measure general capability, not performance on specific tasks a company needs. Every built KateBench — an AI copyeditor trained on 30,000 historical edits — and its 85-90 percent acceptance rate hid a 40-suggestion cap, non-deterministic output, and residual editor work the metric did not capture. The prescription is concrete and unglamorous: pick one recurring job, write five failure modes with gold-standard examples, and test models against those cases. No leaderboard provides this. No frontier model produces it. The eval is company-specific because the work is company-specific.

The model economics reinforce the pressure from a different direction. Fable 5, Anthropic's most expensive model, flatlined at 11 percent of business spending two months after launch. GLM-5.3-Flash, a 320-billion-parameter mixture-of-experts with 18 billion active parameters, approaches Claude Opus 4.8 on coding benchmarks at a fraction of the cost. Open-weight models processed 29 percent of tokens through Vercel's AI Gateway in June, accounting for less than 4 percent of spend. Companies are routing high-volume commodity work to cheaper models and reserving frontier capacity for judgment-dense tasks. The routing decision itself is a filtering act — deciding which work deserves which level of scrutiny, which model, which verification depth. Get it wrong and you either overspend or ship vulnerabilities. Get it right and the economics improve without the quality dropping.

## Who builds the filter

The companies pulling ahead are the ones treating the filter as something to build, not something to buy. Ramp rejected off-the-shelf coding agents and built Inspect, running on remote sandboxes with internal data access, five-second cold starts, and public sessions with no opt-outs. Block built Goose. Stripe built Minions. Shopify built River. The reasoning is consistent: a coding agent that does not understand your codebase, your compliance requirements, or your deployment constraints cannot produce code you can trust without re-verifying it from scratch. The integration with internal systems is the filter. Without it, every generated line arrives as untrusted input.

Every is doing something related with expertise. KateBench encodes an editor's accumulated judgment into an agent that runs a first pass before human review, with tracked changes feeding back into Codex for self-improvement. Twelve Claude Skills built on published consulting frameworks — Minto's Pyramid Principle, Playing to Win, the CIA's Analysis of Competeting Hypotheses — lifted Fable 5 from 38 percent to 97 percent on a partner-level checklist. The frameworks were never secret. McKinsey, BCG, and Bain charge $37 billion a year for advice mostly delivered by associates with under two years of experience. The constraint was the internalization period under partner supervision. Encoding the frameworks as executable skills compresses that. The filter, in this case, is not a code review tool. It is a methodology made repeatable.

The migration stories from this week tell the same story from the production side. Asana's 4,000-file migration, Airbnb's 3,500-file migration, Uber's 600,000-test migration — each one worked because engineers designed the verification loops before the model touched a single file. At Airbnb, 75 percent of files migrated in four hours once the retry loops were built. The remaining 25 percent required human judgment about edge cases the model could not infer. The mechanical work was automated. The filter — the verification system that determined which outputs were correct — was designed, built, and operated by engineers. The model did the typing. The engineers did the trusting, and trusting is harder than typing.

## The discovery problem

Muratori's game engine parallel has a second act worth considering. When production flooded the games market, the industry's response was to build discovery systems — storefronts, recommendation engines, editorial curation. The equivalent in software engineering is the internal eval, the code review pipeline, the routing system that sends the right work to the right model with the right level of verification. These are the discovery systems for AI-generated code: not finding good code among bad, but knowing which generated code is safe to ship and which requires human attention.

The infrastructure layer is consolidating to support this. AgentSky unifies Claude Code, Codex, and other agents behind one API. Monid offers 1,700-plus tools through a single key with transparent pricing. Salesforce and Anthropic's Claudeforce exposes business workflows through MCP servers. The plumbing is standardizing, which means the differentiation moves to the layer above — the evals, the routing logic, the verification depth, the encoded expertise. The companies building that layer are building the filter. The companies buying everything off the shelf are trusting someone else's filter with their codebase.

Background work — the cron jobs, job queues, and message brokers that move operations out of the request path — is evolving in the same direction. What starts as a single scheduled script becomes a distributed system with worker pools and retry logic. The engineering decision is not which pattern to use but when to move between them. AI agents now generate many of those triggers, and the volume is orders of magnitude higher. The filter, in this context, is the architectural judgment that keeps the system reliable as volume grows. The code for each pattern is documented. The decision about when to switch is not.

## What the filter costs

The honest accounting is that verification is now the majority of the work, and it is not getting cheaper. Speculative decoding makes models two to three times faster by pairing a small draft model with a large target model that verifies candidates in a single forward pass. The technique is lossless — the output distribution is provably identical. But acceptance rates vary by workload: 80-90 percent for structured code, under 50 percent for creative writing, and gains that shrink from 1.96x at batch size one to 1.21x at batch size 128. The model got faster. The verification burden did not change. A faster model generating more code means more code to verify, not less time spent verifying.

The companies that understand this are investing in the filter, not the flood. Every's shift from personal agents to a shared Slack-based company agent reflects the realization that maintenance — keeping credentials current, integrations working, memory clean — is the real cost, and it does not scale with model improvements. A stronger model cannot detect that an instruction is outdated or that an integration broke. Walleye Capital made AI use mandatory for all 400 employees, but the CEO's point was institutional, not individual: the company needs to capture what each employee produces with AI, because individual usage that stays in a silo does not compound. Shared usage with feedback loops does. The feedback loop is the filter, and it is the part that compounds.

The games industry survived its production flood by building discovery systems that separated signal from noise. Software engineering is arriving at the same place. The signal is correct, safe, well-architected code. The noise is everything else, now produced at a volume no human team can review line by line. The companies that build the filter — internal evals, verification pipelines, routing logic, encoded expertise — will ship faster because they trust more of what they generate. The companies that do not will drown in plausible-looking code that passes superficial review and fails in production. The flood is here. The filter is the work.
