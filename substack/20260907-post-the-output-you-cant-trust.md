# The output you can't trust

*When the best model scores 30 percent on real science and the best proof takes 90,000 lines nobody can read, the bottleneck has moved past generation — and it is not coming back.*

Claude Opus 5 topped the first Terminal-Bench-Science leaderboard at 30 percent. Seventy tasks contributed by working scientists — analyses, simulations, proofs, code, data products — and the strongest model on the market got fewer than a third right. The benchmark's designers were pleased. When a score is that low, you have a measuring instrument that will still be useful in two years. When a score is 95 percent, you have a press release.

The same week, Terence Tao described a new condition in mathematics. Lech Mazur produced a proof of Sendov's conjecture — a problem about polynomial roots that had resisted experts for decades — formalized in Lean across 90,000 lines. The proof passed formal verification. No human could follow it. Tao worked through it with pen, paper, and AI assistance, extracted the core idea, and produced a 15,000-line version using what he called "surprisingly basic tools." The proof was correct. The understanding was not included. Tao called it proof indigestion: the system produces results faster than humans can digest them.

## The production barrier has fallen

Terminal-Bench-Science and proof indigestion describe the same structural shift from different fields. In science, the bottleneck is no longer running the analysis or writing the simulation — it is knowing whether the output is trustworthy. In mathematics, the bottleneck is no longer finding the proof — it is understanding it. The production barrier has fallen, and what stands behind it is the verification barrier, which is rising.

This is not a complaint about model quality. The models are getting better. The problem is that "better" now means producing more output, not producing more understandable output. The 90,000-line proof is a stronger result than the 15,000-line version in formal terms. It is weaker in human terms. The scientific benchmark's 30 percent score is not a failure of the model. It is a measurement of the gap between what agents can produce and what working scientists can validate as correct scientific work.

Anthropic's own SDLC playbook makes the engineering version of this argument explicit. When an agent writes 5,000 lines in a session, no human can meaningfully review that diff line by line. The traditional quality gate — a senior engineer reading every change — breaks at that volume. Anthropic argues the bottleneck has shifted from code production to planning, testing, security review, and deployment. The human's role moves upstream to specifications and downstream to automated verification. The line-by-line review, the mechanism that gave engineering teams confidence in their code for decades, cannot scale to agent-generated diffs. [The flood and the filter](https://engineeringforward.substack.com/p/the-flood-and-the-filter) traced this shift to its verification consequence: the filter — the evals, the routing logic, the encoded expertise — is now where the engineering work lives. The Terminal-Bench-Science result is the scientific version of the same diagnosis.

## The verification gap is widening

The cache bug that Claude Code fixed this week is a small but instructive example of how invisible the verification problem can become. Tool definitions were being re-rendered after OAuth token refreshes — a mundane authentication detail — which triggered prompt-cache misses roughly once per hour. Each cache miss meant the full context window was re-processed from scratch. For a 20-minute coding session, the cost is negligible. For a multi-hour agent session — the use case Claude Code is built for — the cost compounds into a quiet leak that nobody notices until the billing alarm goes off.

The bug was not in the model. It was in the interaction between authentication infrastructure and the caching layer that makes agentic coding economically viable. Prompt caching is not an optimization. It is the economic foundation. Without it, long sessions become prohibitively expensive. And the infrastructure that supports it — OAuth token schedules, tool definition rendering, context assembly — is where the invisible failures live. A team building agentic systems needs to audit cache hit rates the way a database team audits query plans: regularly, after any infrastructure change, and with the expectation that the problem is probably not where you think it is.

Sunglasses' research on agent context security identifies a more dangerous version of the same invisibility. The security community has been focused on prompt injection — adversarial text that overrides an agent's instructions. But there is a quieter failure: treating relevant context as if it carries authority. A sibling file retrieved to guide a code repair might be relevant to the task while containing hostile instructions. Multiple snippets that appear to be independent sources might share a single origin. Repeated claims of harmless intent in a conversation might accumulate into something the agent reads as permission. The fix is not better filtering of individual inputs. It is provenance: every context record carries its source identity, lineage, trust level, and authorization status. If lineage or permission is missing, the agent stops.

The provenance approach is more principled than injection filtering because it addresses the root cause. But it also makes the verification problem explicit in a way the industry has been avoiding. Every context record needs a trust label. Every retrieval needs an authorization check. Every aggregation needs a provenance audit. The verification burden does not shrink as agents get more capable. It grows, because more capable agents retrieve more context, make more decisions, and act on broader authority. The 30 percent score on Terminal-Bench-Science is a model problem. The missing provenance labels on retrieved context are a systems problem. Both are verification problems. Both are getting harder.

## The harness as partial answer

Two infrastructure projects this week represent attempts to build the verification layer into the agent harness itself. Munder Difflin is an open-source coordinator that wraps existing CLI agents — Claude Code, Codex, Gemini CLI, Kimi, Grok, OpenCode — into a shared system with memory and coordination. The architecture addresses a real problem: when multiple agents work on related tasks without a coordination layer, they produce duplicate pull requests, file conflicting issues, and overwrite each other's work. The "hive mind" provides shared context so agents know what the others have already done.

Warp's Skill Doctor approaches the problem from the opposite direction. Instead of coordinating agents during execution, it reads past conversation transcripts, scores them against rubrics for efficiency and code quality, and proposes concrete diffs to the agent's skill files. The self-improvement loop turns session history into actionable changes. A Series C infrastructure company reported a 30 percent reduction in cost per agent PR after adopting Warp Factories, the team-scale version. The mechanism is straightforward: the tool identifies what went wrong in past sessions and patches the instructions to prevent recurrence.

Both harnesses reduce the verification burden, but neither eliminates it. Munder Difflin coordinates agents so they do not duplicate work, but the coordination layer itself needs verification — is the shared memory accurate, are the task decompositions correct, is the "Michael" orchestrator agent making sound delegation decisions? Skill Doctor improves skills from past data, but the rubrics that score sessions are themselves judgments that need calibration. The harness reduces the surface area of the verification problem. It does not remove it.

Daniel Blum's Claude Cowork system for product managers demonstrates what the end state looks like when the verification loop is fully internalized. His system handles 70-80 percent of his workday — managing a Notion board, generating morning briefs, scanning Slack and email for context gaps. The self-improvement loop compares Claude's original drafts with the versions Blum actually sent, learning from the edits without requiring explicit feedback. The system identifies its own knowledge gaps: when it encounters an unfamiliar term in Slack, it reads the relevant thread, understands the general idea, and asks a targeted question to confirm the meaning before saving it.

The architecture principle is that context is not a one-time setup but an ongoing system. Blum spent months feeding Claude voice memos, links, and brain dumps to build context files, then created recurring updates that refresh them. The self-improvement loop runs weekly. The gap detection runs daily. The verification is continuous and built into the workflow rather than applied after the fact. The biggest remaining limitation is not intelligence but persistence: Claude cannot reliably continue working when his computer is off. When that barrier falls, the system is ready — it already understands what completed work looks like.

## The reasoning question underneath

Thore Graepel's departure from DeepMind to build a reasoning-first AI venture is the foundational version of the verification problem. His argument is that current large language models do not actually reason — they approximate reasoning through pattern matching. The architectures that powered AlphaGo a decade ago relied on search, planning, and deliberation. Today's autoregressive models predict the next token. Graepel believes the architecture needs fundamental redesign, not just more parameters.

His AlphaGo collaborator David Silver already left to found Ineffable Intelligence on the same thesis. Laurent Sifre, another DeepMind alumnus who cofounded Paris-based H Company, took a different path: he joined Microsoft to build a Paris AI research team. The DeepMind diaspora is splitting between those who believe the current paradigm can be fixed and those who believe it needs replacement. Graepel and Silver are betting on replacement. Sifre is betting that Microsoft's resources and a Paris-based team can push the existing paradigm further. Both bets are informed by the same observation: the verification gap is a symptom of a deeper limitation. A model that cannot reason cannot produce output that is verifiable by reasoning.

Every's experiment with cloning coworkers captures the practical stakes. Companies are beginning to capture their best performers' judgment as reusable AI skills — not just automating tool use, but encoding how a specific person makes decisions. The value proposition is institutional persistence: when a key person leaves, their judgment stays. The questions are equally significant. Who owns a skill derived from a person's professional judgment? What consent is required? Does cloning a coworker's expertise train their replacement? [The method walks out the door](https://engineeringforward.substack.com/p/the-method-walks-out-the-door) described what happens when expertise becomes encodable: the method becomes portable, and the person who carried it becomes optional. The cloning experiment is the organizational version of the same shift — and it depends entirely on whether the encoded judgment is good enough to substitute for the human version. That is a verification question nobody has answered.

## The linguistic contamination

Louisa Abraham's analysis of 47,000 GitHub PRs found that a word cluster nonexistent in 2025 now appears in 45 percent of human-authored PRs. The top word is "load-bearing," used in its metaphorical sense — "load-bearing assumption," "load-bearing paragraph" — a usage pattern that originated in AI-generated text, particularly Claude's, and has since been adopted by humans who read and write alongside AI systems. This is not AI-generated content detection. It is the detection of AI writing patterns seeping into human writing.

The finding has a direct connection to the verification problem. If human communication in software engineering is absorbing AI vocabulary patterns, the boundary between "human-written" and "AI-written" is blurring — not because AI is imitating humans better, but because humans are imitating AI. When a human writes "load-bearing assumption" in a pull request, they are using a phrase that carries no structural meaning in pre-AI English. It is a linguistic marker of a worldview shaped by AI output. The verification question is not just whether the code is correct. It is whether the human reviewing the code is thinking independently or reproducing patterns absorbed from the system being reviewed. OpenAI's decision to wind down Cursor model access following SpaceX's acquisition adds a competitive dimension: the tools developers use shape how they think, and control over those tools is becoming a strategic lever. When 5 percent of Cursor's traffic runs on OpenAI models and those models are being withdrawn, the question is not just about market share. It is about whose patterns are shaping the next generation of engineering communication.

## The measurement we have not built

Terminal-Bench-Science is valuable precisely because 30 percent is a low score. The benchmark will measure progress for years. But the benchmark tests scientific tasks — analyses, simulations, proofs — that have verifiable answers. Most real-world agent work does not. A code review is not verifiable in the way a mathematical proof is. A product specification is not verifiable in the way a scientific simulation is. The verification methods that work for science and mathematics — formal proof systems, peer review, reproducible experiments — do not map cleanly onto the judgment-dense work that agents are increasingly asked to do.

The companies that figure out how to verify agent output in domains without clean answers will scale their AI usage. The companies that do not will create bottlenecks that make agentic work slower than manual work. Anthropic's SDLC playbook, Warp's Skill Doctor, Sunglasses' provenance framework, and Daniel Blum's self-improving Cowork system are four different approaches to the same problem. None is complete. None will be. The verification gap is not a bug to be fixed. It is the permanent condition of working with systems that produce more than their operators can understand. The work is learning to live in that condition without pretending it does not exist.
