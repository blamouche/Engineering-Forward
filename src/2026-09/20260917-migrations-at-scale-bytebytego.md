# Migrations at Scale: Changing the Application Engine at 30,000 Feet
**Source**: ByteByteGo (bytebytego@substack.com) — https://blog.bytebytego.com/p/migrations-at-scale-changing-the
**Date**: 2026-09-17
**Author**: ByteByteGo
**Keywords**: database migration, zero-downtime, dual-write, change data capture, CDC, expand-contract, shadow table, backfill, gh-ost, pt-osc, online schema change

## Elevator pitch
A comprehensive guide to running production database migrations without taking the system offline, covering the three core strategies — shadow table swaps, expand-contract, and change data capture — that let engineering teams change a working system while the service people depend on keeps running.

## Takeaways
- **The fundamental tension is exclusivity vs. availability**: Schema changes need exclusive access to tables; production needs continuous availability. At scale, copying existing data can take days, and many supporting applications depend on the component being replaced. Every intermediate step must work while ordinary business continues.
- **Shadow table swap isolates schema changes**: Build a copy of the table with the new schema, keep it synchronized with live writes via triggers (pt-osc) or binlog tailing (gh-ost, Spirit), then atomically RENAME the copy in place. Production traffic only sees a sub-second cutover. GitHub built gh-ost after trigger-based tools caused deadlocks on tables with billions of rows.
- **Expand-contract decouples data transformation from deployment**: Add new columns or tables alongside old ones (expand), dual-write to both, backfill old rows in throttled batches, dual-read from both, then remove legacy structures (contract). Every stage is independently reversible and deployable. Stripe uses a four-phase variant: dual-write → change reads → change writes → drop legacy.
- **CDC enables near-real-time replication**: Change Data Capture tools like Debezium read from the database's write-ahead log or binary log, streaming changes to Kafka topics. Squarespace used this to migrate from Postgres to CockroachDB with no write downtime — Debezium connectors per table, Apache Beam consumers writing to CRDB, and a fallback pipeline mirroring back to Postgres as a safety net.
- **Backfill jobs are where migrations fall over**: Four invariants from Stripe and GitHub: idempotent (safe to re-run), resumable (checkpoint per batch), throttled (watch replica lag, back off exponentially), and primary-key ordered (avoid full table scans). Without these, a "we have a plan" migration breaks in production.
- **Verification is non-negotiable**: Scientist-style runtime comparison, double-read diffing (Slack's approach), or pre-cutover checksums. GitHub's gh-ost includes a test-on-replica mode to validate new schema with real data without touching the primary.

## Synthesis
ByteByteGo's article tackles one of the hardest problems in production engineering: changing a working system while the service people depend on keeps running. The framing is concrete — a successful online shopping platform has outgrown its original database, order histories load slowly, maintenance takes too long, and engineers spend too much time managing the system's limitations. The team wants to migrate to a new database, but the shop can't be taken offline. This scenario illustrates the core challenge: at scale, copying existing data can take days, and every intermediate step must work while business continues.

The article identifies three core strategies that together cover almost every production migration. The shadow table approach handles schema changes: pt-online-schema-change (pt-osc) uses MySQL triggers to synchronously mirror DML into a shadow table, while gh-ost (GitHub) and Spirit (Block) avoid triggers entirely by tailing the MySQL binary log. The trigger-based approach works for moderate throughput but serializes writes at high volume — GitHub built gh-ost after trigger contention caused deadlocks on commits and pull_requests tables with billions of rows. The binlog-based approach reads from a replica to keep migration overhead off the write path, supports runtime throttling via Unix socket, and includes a test-on-replica mode. The cutover uses a dual-block sentry table protocol that's safe even if the migration process dies mid-swap.

For changes that also involve data transformation (combining columns, splitting values, populating computed fields), the expand-contract pattern decouples the change into independently deployable stages. Stage 1 adds the new structure while keeping the old one intact, with application v2 dual-writing to both. Stage 2 backfills old rows in throttled batches, then deploys app v3 to read from the new column. Stage 3 removes the legacy structure. Stripe's variant adds an explicit verification step between each phase, and emphasizes keeping each rollout small — "we never attempt to change more than a few hundred lines of code at one time."

Change Data Capture has emerged as the backbone for cross-database migrations. Squarespace's migration from Postgres to CockroachDB used Debezium connectors reading from Postgres's WAL via the pgoutput logical decoding plugin, funneling changes into Kafka topics in Avro format. Apache Beam pipelines consumed events and wrote to CRDB with batched upserts, achieving >99.99% data freshness by cutover. A fallback pipeline mirrored changes back to Postgres as a safety net. The team hit referential integrity challenges when independent writers for related tables fell out of sync — their solution was temporarily disabling constraints during the isolated migration process and re-enabling them before cutover.

The article concludes that database migrations at scale reduce to one principle: isolate change from production traffic through incremental, reversible steps. The production patterns — verification via Scientist-style comparison, throttled backfills, careful cutover coordination — exist because migrations fail. GitHub built gh-ost after trigger-based tools caused deadlocks. Slack built double-read diffing because dual-write alone caught fewer bugs than expected. Figma built custom sharding after concluding NewSQL migrations carried more risk than incremental sharding on Postgres. The lesson: plan for failure, keep old structures for 24–48 hours, and rehearse rollback before starting.
