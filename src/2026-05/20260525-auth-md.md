# auth.md

**Date**: Unknown
**Author**: WorkOS

## Elevator pitch
WorkOS proposes auth.md — an open Markdown-based protocol that lets AI agents discover how to register users on any application without a sign-up form, by publishing supported flows, scopes, and endpoints at a well-known URL, composing existing OAuth standards for agent-native authentication.

## Takeaways
- auth.md is a well-known file (like robots.txt) that apps host at their domain, telling agents which registration flows are supported, what scopes exist, and how to obtain credentials
- Two registration flows: "agent verified" (identity provider vouches for user, no human interaction) and "user claimed" (OTP-based human confirmation)
- Apps issue scoped API keys or access tokens tied to users — auditable, expirable, revocable
- The protocol is open and not tied to WorkOS infrastructure — it composes existing OAuth standards (Protected Resource Metadata, ID-JAG identity assertions)
- Any app can publish auth.md, and any agent can read it with no WorkOS account required
- Represents a category-defining move: what robots.txt was for web crawlers, auth.md aims to be for agent-to-app registration

## Synthesis
WorkOS is making a play to become infrastructure for the agent-native web with auth.md, a protocol that formalizes how AI agents discover and execute user registration on behalf of humans. The core insight is simple but powerful: as agents become the interface layer between users and services, the traditional sign-up form — email, password, CAPTCHA, email verification — becomes a bottleneck designed for humans that agents can't easily navigate. auth.md replaces that with a machine-readable declaration of registration capabilities.

The protocol defines a Markdown file hosted at the application's root domain that declares supported authentication flows. There are two primary flows. The "agent verified" flow is the truly novel one: the agent's identity provider (think: Claude, ChatGPT, or a third-party auth service) cryptographically asserts the user's identity, and the target application trusts that assertion — no human interaction required. The "user claimed" flow is more conventional: the agent triggers a one-time code sent to the user's email or phone, the human confirms ownership, and the account is linked.

Credential issuance is deliberately flexible. The service decides whether to return scoped API keys or access tokens, allowing reuse of existing API authentication infrastructure. This is a smart architectural choice — auth.md doesn't ask applications to rip out their auth stack; it adds an agent-compatible layer on top.

The open-protocol positioning is critical. By publishing the spec on GitHub and composing existing OAuth standards rather than inventing new ones, WorkOS is attempting to make auth.md an industry standard, not a company-specific feature. The analogy to robots.txt is apt: a simple, well-known, machine-readable convention that became universal because it solved a clear coordination problem with minimal implementation burden.

The implications are significant. If auth.md (or something like it) becomes standard, it accelerates the agent-native economy by removing the last human-required step in user onboarding. An agent could sign a new user up for a SaaS product, issue API keys, configure scopes, and start making API calls — all programmatically, without the human ever seeing a registration form. This is authentication infrastructure catching up to where the rest of the agent stack is heading.
