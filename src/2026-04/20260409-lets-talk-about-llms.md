# Let’s talk about LLMs

**Source**: https://www.b-list.org/weblog/2026/apr/09/llms
**Date**: April 9, 2026
**Author**: James Bennett
**Keywords**: LLMs, software engineering, no silver bullet, automatic programming, productivity, programming profession

## Elevator pitch
James Bennett argues that the strongest historical lens for evaluating LLM coding claims is still Fred Brooks: faster code generation may cut accidental difficulty, but it does not remove the essential work of specification, design, and testing that makes software hard.

## Takeaways
- Bennett deliberately focuses on LLMs rather than the broader and vaguer term “AI.”
- He revives Fred Brooks’s “No Silver Bullet” argument to question claims of order-of-magnitude gains from code generation alone.
- The essay treats many current LLM-coding promises as a modern form of automatic programming hype.
- The main bottleneck in software is framed as conceptual work—requirements, design, tradeoffs, testing—not raw code transcription.
- Even strong code generation may therefore shift software work more than it eliminates it.

## Synthesis
Bennett’s essay is useful because it drags the current LLM coding debate back onto historically solid ground. Rather than arguing from anecdotes, vibes, or tribal allegiance, he asks a more durable question: what part of software work are LLMs actually accelerating? Fred Brooks’s distinction between accidental and essential complexity remains a sharp lens here. If software is hard mainly because of specification, design, and conceptual integrity, then faster code generation can only move the ceiling so far.

That does not make LLMs unimportant. It makes their impact more legible. Bennett is effectively arguing that many people are over-crediting LLMs for a part of the workflow that has already been steadily compressed by higher-level languages, frameworks, scaffolding, and tooling. The coding surface still matters, but in many mature environments it is no longer where most of the time goes. The work that dominates remains understanding what to build, negotiating constraints, validating behavior, and adapting systems after reality collides with the first draft.

The comparison to automatic programming is especially apt. Every generation of tooling produces a new hope that the act of expressing solutions will vanish as a bottleneck and that software creation will become mostly a matter of stating intent. Sometimes that hope is partially realized. But each leap tends to reveal that the real burden lies in sharpening the intent itself. LLMs may therefore be more like a powerful new high-level language than like a total break from previous software economics.

The bigger lesson is cultural. A lot of the current discourse treats skepticism about LLMs as stodgy resistance or treats enthusiasm as inevitable realism. Bennett offers a better posture: acknowledge the gains, but do not confuse speed in one layer with the elimination of difficulty in the whole system. That is a much healthier way to reason about what these tools change in software engineering and what they almost certainly do not.
