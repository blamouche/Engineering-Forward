## Synthesis
How is search implemented where you work? Probably as a complex set of capabilities on top of retrieval. Our search APIs understand queries, call backend search systems, and finally rerank results. But if we had an agent in the loop, would we need all that? Could we replace search backends with an agent? After all, an agent understands user requests, calls retrieval tools, and evaluates relevance on its own. We see ChatGPT do this all the time, why can’t our search bar? In other words, if you give a basic BM25 backend to an agent, could it take the Search API’s job? Surprisingly good results with simple tool usage Well I’ve measured initial findings (a bit deeper than in the past ). I gave agents basic search tools and got the popcorn out to watch. On Amazon ESCI, we see increasing performance with slightly better retrievers + LLMs. First, we start with a bm25+ e5_embedding baseline. They achieve 0.289/0.314 NDCG respectively. Then we measure three agentic experiments. Each with GPT-5-mini driving different combinations of search tools. We see an agent with e5 embeddings get 0.359 and with BM25 0.385. With both we get 0.410. GPT-5 with both tools gets an NDCG of 0.453. What’s amazing about this? I’ve barely lifted a finger. I just set up a stock LLM with some search tools. Nothing here has been fit to my data. A 0.289→0.453 jump in quality depends only on model quality + simple retrievers. If an agent could be fast enough, is there a future here we build search with agents and not APIs? A world where agents reason about queries to show users the best results? But, agents call search approximately… once? What kind of ingenious strategies are these agents employing? It turns out, for the most part, they call each search tool roughly once: When you look at reasoning traces, you see the agent interpret the search, issue a single query, retrieve up to the max of 20 results, then rank them. Occasionally, very rarely, with just BM25, you’ll see two simultaneous searches.
