# Code is Cheap(er)
**Source**: https://htmx.org/essays/code-is-cheap/
**Date**: 2026-06-04
**Author**: Carson Gross (htmx)
**Keywords**: ai-coding, code-generation, complexity, software-engineering, subtractive-engineering, llm, understanding

## Elevator pitch
htmx creator Carson Gross argues that while AI has made code dramatically cheaper to produce, understanding code has become more expensive — and proposes the "subtractive, constraining engineer" who prides themselves on the code they remove rather than create, as complexity remains the apex predator.

## Takeaways
- Code has gotten much cheaper to create with AI tools, but understanding code has become more expensive because generated code has no inherent understanding — it must be read after it's written
- The "compilers are deterministic" defense fails: LLMs are non-deterministic, LLM workflows typically don't retain original source, and LLM output is generalized software rather than narrowly constrained machine code
- LLMs can produce code far faster than any human can understand it, making incremental use safer than allowing massive changelists
- The "Sorcerer's Apprentice" metaphor applies: you want to be the sorcerer who understands the magic, not the apprentice who loses control of it
- Complexity remains the apex predator — LLMs are prolific coders incapable of fear of complexity, a dangerous combination
- The proposed solution is the subtractive, constraining engineer: says no, closely examines LLM output, suggests simplifications, and prides themselves on code removed or prevented from entering systems

## Synthesis
Carson Gross, creator of htmx, published "Code is Cheap(er)" on June 4, 2026, offering a measured perspective on what AI code generation means for software developers. The essay acknowledges an uncomfortable truth: in the last year, code has gotten much cheaper to create. AI can generate reams of reasonably decent code incredibly quickly, and there is no point pretending this isn't the case. But rather than dismissing this shift with "coding was never the problem," Gross takes the implications seriously.

The central observation is that while code has gotten cheaper to create, understanding code has become more expensive. When code is generated by an LLM rather than emerging painfully from a programmer's fingers, there is no inherent understanding of that code. If understanding needs to exist, it must be done after the code is written, by reading it. And conventional wisdom says reading someone else's code is harder than writing your own. Gross rejects the AI enthusiast's defense that "you don't understand the output of compilers either," identifying it as a category error for three reasons: compilers are deterministic while LLMs are not, compiler workflows retain their original source code while LLM workflows typically do not, and compiler output is to a narrowly constrained domain (machine code) while LLM output is generalized software.

The danger is that LLMs can produce code far faster than anyone can understand it. Gross recommends incremental use of LLMs rather than allowing them to generate massive changelists that neither the developer nor anyone else can understand. While there are exceptions — mechanical refactors where this can be appropriate — it is extremely dangerous when new semantics are being introduced into a codebase.

The essay invokes the Sorcerer's Apprentice from Disney's Fantasia as an apt metaphor for the AI era. The apprentice uses magic to assist with drudgery, enchanting a broom that starts cleaning vigorously until things spiral out of control. The chaos is resolved when the Sorcerer reappears and asserts control. The lesson: you want to be a sorcerer, not an apprentice, and a sorcerer has to understand the code.

The deeper concern is complexity. Humans have a poor grasp of geometric and exponential curves, which is why they believe in fairy tales like compound interest. The core danger of cheap code is complexity, which tends to grow at least geometrically and often exponentially with the size of a system. Before LLMs, there were prolific human coders who lacked a proper fear of complexity — Gross has seen them heap code on top of problems until systems collapse into unmodifiable steady states. LLMs are incapable of fear of complexity, and they are prolific coders. That combination is dangerous.

The proposed response is the subtractive, constraining engineer: one who says no, closely examines LLM output, suggests simplifications, and retains a firm hand when dealing with generated code. Rather than priding themselves on the code they create, this engineer prides themselves on the code and layers they remove or prevent from entering systems. The ethos is more sculptor than builder — subtractive rather than additive. At the system design level, the builder ethos still applies for composing components, but even there the subtractive mindset is useful for removing unnecessary components and simplifying inter-component interactions.
