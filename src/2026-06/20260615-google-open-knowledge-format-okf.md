# Introducing the Open Knowledge Format (OKF): A Portable Standard for AI Agent Context
**Source**: https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing/
**Date**: 2026-06-15
**Author**: Sam McVeety, Amir Hormati (Google Cloud Data Cloud team)
**Keywords**: Open Knowledge Format, OKF, Google, markdown, YAML frontmatter, AI agents, context, LLM wiki, interoperability, knowledge management

## Elevator pitch
Google introduces the Open Knowledge Format (OKF) v0.1—an open specification that formalizes the "LLM wiki" pattern (championed by Andrej Karpathy) into a portable, vendor-neutral standard: knowledge as markdown files with YAML frontmatter, designed to be produced by any system and consumed by any AI agent without translation layers.

## Takeaways
- OKF represents knowledge as a directory of markdown files, each with YAML frontmatter for structured fields (type, title, description, resource, tags, timestamp) and a markdown body for everything else
- The format is deliberately minimal: only one field is required (`type`), everything else is left to the producer—maximizing adoption flexibility while ensuring interoperability at the document level
- Three design principles: minimally opinionated, producer/consumer independence, and format-not-platform—OKF is a spec, not a service
- Reference implementations include a BigQuery enrichment agent (walks datasets, drafts OKF concepts, enriches with citations) and a static HTML visualizer that turns any OKF bundle into an interactive graph
- Three sample bundles published: GA4 e-commerce, Stack Overflow, and Bitcoin public datasets—demonstrating OKF across different knowledge domains
- The pattern formalizes what teams already do ad hoc: Obsidian vaults wired to coding agents, AGENTS.md/CLAUDE.md convention files, metadata-as-code repos—the goal is to make these interoperable

## Synthesis
OKF addresses a real and growing pain point in AI engineering: context fragmentation. Every team building AI agents eventually reinvents the same solution—a markdown wiki that the agent reads before acting. Karpathy's LLM Wiki gist articulated the pattern: LLMs don't get bored, don't forget to update cross-references, and can touch 15 files in one pass, making them ideal wiki maintainers. But each implementation is bespoke; there's no way for a wiki produced by one team's agent to be consumed by another team's agent without manual translation.

OKF's insight is that the missing layer is a format, not a platform. The spec fits on a single page: markdown files with YAML frontmatter, one concept per file, file path as identity, markdown links for cross-references, optional index.md and log.md files. This is close to what most teams already do—the value is in agreeing on the small set of conventions (what fields exist, what filenames mean) that enable interoperability without requiring anyone to adopt a new tool.

The producer/consumer separation is architecturally clean. A human can hand-author OKF, an LLM can generate it, a metadata export pipeline can produce it—and any of these can be consumed by any agent, visualizer, or search index that understands the format. This is the same design philosophy that made REST successful: define the contract, let the implementations vary.

The BigQuery enrichment agent reference implementation is particularly relevant for data teams. It walks a BigQuery dataset, drafts a concept document for every table and view, then runs a second LLM pass to enrich each concept with citations, schemas, and join paths. This is the pattern data engineering teams need: automated documentation that stays current because it's generated by the same LLMs that consume it.

For engineering teams, OKF offers a lightweight standardization path for the agent-context problem. Rather than building bespoke knowledge bases per project, teams can adopt OKF conventions and benefit from cross-project and cross-tool interoperability. The spec is open, the reference implementations are on GitHub, and the barrier to entry is a markdown file with a `type` field. The risk is adoption: OKF competes with every team's existing ad hoc solution, and network effects only materialize if enough producers and consumers adopt the format.
